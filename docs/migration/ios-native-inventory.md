# Local iOS native inventory — pilot 02A

Audited November 10, 2026 (America/New_York) for [issue #3](https://github.com/dvale94/kyrshas-app/issues/3), against fetched `main` at `25122c389fa766a0c6019e93057b4d77dc90a9dc` (including audit PR #2). This is a documentation-only inspection of the **real local, Git-ignored `ios/` directory**. A GitHub checkout cannot reproduce this evidence: Git tracks zero native files. No native project, backup, dependency, configuration or lockfile was modified.

## Recommendation and confidence

**Represent the discovered settings in Expo configuration/plugins, then conditionally regenerate in a separate approved workspace and selectively port behavior. Preserve the original native tree and backup.** No bespoke native business logic or additional application/extension target was found in the inspected first-party sources/project. This supports the prior [audit's](expo-audit.md) fresh-scaffold direction, but does not make the current `app.json` sufficient to reproduce the native app.

An independent local backup existence/content check passed (details below). Regeneration is still **not safe as an unconditional replacement of this directory**: tablet targeting, display name, version metadata, transport policy and native asset provenance need resolution before accepting a replacement. No regeneration or migration implementation is approved by this report. If later comparison reveals required native behavior that config/plugins cannot express, preserve and port it through a maintained native module/plugin, or reconsider the incremental path.

Confidence: **high** for the enumerated file contents and configuration differences; **moderate** that bootstrap/Pods infrastructure is generated/default-like; **low/unverified** for parity with a shipped binary, externally registered capabilities, runtime behavior and storage. No clean template was generated or downloaded to establish exact template identity or authorship.

- Read-only inspection covered `ios/kyrshasApp.xcodeproj/project.pbxproj`, both workspace metadata files, the shared scheme, all first-party Obj-C/Obj-C++/Swift/header sources, `Info.plist`, entitlements, `Supporting/Expo.plist`, `Podfile`, `Podfile.lock`, `Podfile.properties.json`, linked source/resource/framework references, splash storyboard/assets, generated Expo module-provider metadata, and Xcode environment variable names/path-presence flags.
- The separate backup directory was found outside the Git worktree. Its exact location and private values are intentionally omitted. Its resolved root differs from `ios/`, the root is not a symlink, and all **16,134 regular-file pairs have distinct inodes**. All **20,437 relative path/type/content-or-link-target entries** match between original and backup, including **2,626 symlinks**; the remaining entries are directories. All 27 first-party regular files outside `Pods/`, `build/` and `xcuserdata/` are present and byte-identical.
- SHA-256 file/link fingerprints were held in a temporary file outside Git for the final unchanged-tree check. Symlink targets were compared as text; their external destinations were not recursively backed up or validated. This establishes a separate matching local copy, not an off-device backup, restore test, permission/xattr preservation, or recoverability of account credentials and installed app data.
- Inspection scripts emitted selected safe fields, presence/equality booleans, structural code and public dependency versions. Signing values, app/account identifiers, environment values, personal content and backup paths were suppressed. No keychain, developer account, provisioning service, API, build or app was accessed.

## Config/plugin mapping and limits

The table identifies proposed representations, not installed plugins or tested output. Expo's [app configuration reference](https://docs.expo.dev/versions/latest/config/app/) documents identity, version, scheme, device support and plist/entitlements configuration. The [build-properties plugin](https://docs.expo.dev/versions/latest/sdk/build-properties/) supplies build customization during Prebuild, and [splash-screen documentation](https://docs.expo.dev/versions/latest/sdk/splash-screen/) recommends its config plugin. These are current references; select and validate the options supported by the **chosen future SDK**, rather than applying latest examples to Expo 49.

Expo's [Continuous Native Generation guidance](https://docs.expo.dev/workflow/continuous-native-generation/) explains that reproducible native changes belong in config/plugins. Our source-based recommendation is to use that route for confirmed settings, with native code porting only if later evidence requires it. No old Podfile, Xcode flags, identity, signing relationship or asset should be discarded merely because it looks generated.

## Material decisions and next-phase gates

1. Confirm intended phone/tablet and orientation behavior, and the intended display name/version baseline, given the recorded config/native differences. Existing documents describe tablet intent; the local target provides contradictory evidence. No behavior choice is made here.
2. Approve the transport policy and any intentional security change separately; do not silently carry the broad ATS exemption into a production baseline. The prior audit's tracked client-credential exposure remains unresolved and was not used, printed or rotated.
3. Approve a chosen SDK/migration scope and a secure identity/signing preservation process. Account registrations, provisioning, shipped entitlements and the highest distributed build number require authorized external evidence; local strings cannot establish them.

After those decisions, a proposed isolated scaffold can be compared with the preserved original. Acceptance must include native settings/resource comparison, approved icon/splash visual review (decoded pixel comparison was unavailable locally), scheme/URL behavior, device/tablet tests, installed-app storage/upgrade tests and safe API fixtures. Device execution, signed builds, account checks and backup restore were **NOT RUN**. These are migration gates, not blockers to reviewing this documentation PR.
